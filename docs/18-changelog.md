| 2026-09-05 (13) | **v0 built — four zones, LEDs, no water.** The roadmap's bench prototype now exists: a pure host-tested core (`components/irrigation_core/`), an independent guard (`components/irrigation_guard/`), a scheduler (`components/irrigation_scheduler/`), five YAML packages and a **61-test** host suite that runs in ~0.2 s with no toolchain. Firmware **941 KB = 51.3 %** of the 1.75 MB app partition, static RAM 30.5 %, ~85 entities. **Three findings worth recording.** (a) **The simulated season found a real bug** — latching a CRITICAL refused the *next* run but left the current one open, i.e. the valve that raised the alarm stayed open; `latch_critical()` and `set_winter()` now abort the run and report whether they did. (b) **`lib/irrigation_core/` cannot work as specified** — ESPHome only gathers sources belonging to a component package, so the core is a config-less *component* instead, keeping one copy shared by the host tests and the device build. (c) **Direct GPIO for the zones on the bench, not the PCF8574** — the guard can only hard-close pins it writes itself, and behind an expander its raw sweep would cover the master valve alone. Also: the safe-mode pin sweep is now **generated from the guard's own config** so it cannot drift, `catch_up_window` (60 min) is a new v0 decision that the requirements never bounded, and rows 7–9 and 11 of the fault policy are explicitly **deferred to v1** for want of a flow meter. Bench procedure in [§21](21-bench-procedure.md). |

| 2026-09-05 (11) | **Capacity answer refined — the constraint is not where the first pass said.** Corrected the RAM figure: ~130 entities is **≈13–32 KB, not ≈11 KB** (the earlier number counted only `EntityBase`, not the instantiated component). More importantly, **entity count is not a heap problem at all — it is a ListEntities enumeration problem**, and ~130 entities sits close to where real devices have failed: verified reports of entities silently missing after connect (~250 → only 120–140 visible) and a task-watchdog reboot from the loop spinning on a full TCP buffer. New risk **R24**; **NFR-M8 now pins a minimum ESPHome of 2026.9** (fixes #18577 and #18802/3) — note the pool controller runs 2026.7.2, predating both. Also: **alarm on `debug.block`, not `free`** — every documented failure is a contiguity failure, not a total-free-bytes one — and `min_free` requires ≥2026.2.0. |
| 2026-09-05 (10) | **Capacity question answered, and a P0 bug found in the process.** The ESP32-WROOM-32 is **comfortably sufficient** — **1.75 MB app partition [V]** against a ~1.02–1.29 MB build (**28–43 % headroom**), ~130 entities cost **≈11 KB** of a ~150–220 KB heap (`sizeof(EntityBase)` ≈ 20 B, names in flash), no entity-count ceiling; watch-thresholds documented. **But the deadman as specified could not have worked (new risk R1b):** LEDC free-runs, so a hung loop would leave the wave running and the valve rail enabled, and toggling from `loop()` is capped at ~31 Hz which the charge pump resolves to ~1.75 V, below V<sub>GS(th)</sub>. Redesigned as an **independent `esp_timer` heartbeat driving a retriggerable monostable**; **E6 upgraded** to require proving it under a deliberately hung firmware. Also: **OTA calls `App.feed_wdt()` inside its blocking loop [V]** — the watchdog is silenced while the supervisor is stopped, so OTA must be forbidden during a run. Three corrections: **NVS is 112/96 sectors, not 109/5** (the "20× weaker Arduino NVS" argument is dead), **ESP32-S3 has 4 PCNT units, not none** (only the C3 has none), and `pulse_meter` is ISR-based rather than PCNT. |

Wiring via a second PCF8574 (already in the BOM). Added to §20 as optional group 6, **€70**; optional total €216 → €286. Moved physical control from v2 to v1-optional. |

| 2026-09-05 (4) | **Found and fixed a latent safety bug surfaced by asking whether a cycle can exceed 2 h 40 — it can.** The max-runtime backstop had been specified "in the 24 VAC common"; since the master valve stays energised across a whole cycle, a 45-min latching timer there would **trip mid-cycle and shut the garden down**. Moved to the **zone-side common**, where it bounds a single zone run and the inter-zone settle gap resets it. The settle delay is consequently promoted to a safety requirement (FR-4.3). Added FR-4.7: no component may assume a bounded cycle duration; the constraint on a cycle is its *latest finish*, not its length. Also noted that the "05:00–07:00 window" was itself an unstated assumption. |
